# Архитектура

Browser → FastAPI:8000 → PostgreSQL. Next.js собирает статические страницы в Docker build stage, затем готовые файлы копируются в Python image. Runtime Node не нужен. API и frontend имеют один origin, CORS не открывается.

`app/db.py` — нормализованные SQLAlchemy Core таблицы и пул соединений; `migrations/` — версионные Alembic-миграции; `app/security.py` — Argon2id, сессии, роли; `app/service.py` — валидация, резервирование, переходы состояний, аналитика; `app/api.py` — API; `app/ai.py` — внешние AI-адаптеры; `app/telegram_service.py` и `bot.py` — Telegram; `worker.py` — разрешённые фоновые операции.

Основные IDs — integer sequences PostgreSQL: достаточны для заданного масштаба, внешние TikTok ID хранятся строками. UTC timestamps на всех новых таблицах. Пароли TikTok не хранятся. Для ручного комментария без внешнего ID вычисляется SHA256 из кампании, видео, автора и текста; изменение этих данных может обойти такую дедупликацию, поэтому стабильный внешний ID предпочтительнее.

`(platform, external_comment_id, campaign_id)` уникален в БД. На исходный комментарий создаётся один черновик. Захват делается условным UPDATE … RETURNING, PostgreSQL сериализует конкурентную запись. Публикация сохраняет одну запись на draft_id и уникальный idempotency key, только в транзакции. Фактическую ручную публикацию вне приложения заблокировать или проверить нельзя.

Redis и Celery включаются профилем jobs, Telegram polling — integrations. Диспетчер выбирает задачи с FOR UPDATE SKIP LOCKED, резервирует до трёх минут и посылает в Celery. Только безопасно повторяемые чтения/проверки выполняются в worker. После падения задачи возвращаются по lease. Диспетчер раз в 15 секунд; задержка нормальна. Web не имеет доступа к Docker socket.

Миграция не удаляет старые items/audit. Архив показывает до 200 старых записей. Первое создание схемы через Alembic не является заменой будущих миграций: последующие изменения должны добавлять новую revision. Downgrade с удалением таблиц отключён.
